# B2B 风控与服务质检后台：架构融合提案

> 文档状态：面向比赛 MVP 的架构提案，不代表相关功能已经实现。

2026-10-11 已确认每份报告评价一次订单或咨询轮次，长聊天线程先经独立切分器处理；D6 默认纳入任务，Hook 只提供线索。三人分工、实际数据映射和待实现接口见 [模块接口约定](TEAM_DEVELOPMENT_CONTRACT.md)。

## 1. 产品定位

产品面向在线心理咨询平台的平台方。比赛 MVP 假设只有一个平台工作空间和一个质检操作员账号，由该操作员配置评价规则、查看自动质检结果、处理高风险或低置信案例，并追溯模型结论对应的会话证据。

系统减少人工逐条筛查的工作量，采用“自动初筛和评价 + 人工处理需要复核的案例”的工作方式。评价结果是质检线索；指标和风险规则应由业务及心理咨询专业人员审核，系统不作临床诊断，也不应让未复核的模型评分直接触发处罚。

## 2. 核心业务闭环

1. 唯一质检操作员接入或导入已授权的咨询记录。
2. 后端校验格式、来源和访问凭据，规范化消息并执行必要的脱敏。
3. 后端根据可信元数据识别初诊/复诊；复诊时按授权读取历史咨询片段并以独立来源上下文注入 Agent messages。
4. 风险监测 Hook 可在常规评价前扫描本次会话并提供线索；D6.1/D6.2 默认纳入任务，不受 Hook 状态控制。
5. 确定性路由器按固定归属分配指标：专业服务评价 Agent 负责 D1/D3/D6.2，过程与响应评价 Agent 负责 D2/D5，共情与关系评价 Agent 负责 D4/D6.1；各 Agent 返回结构化结论及消息证据。
6. 一个证据核验子 Agent 将复合评价拆成最小事实，统一完成原文定位、支持/矛盾/证据不足判断、适用性与评分锚点核查；应用编排器控制一次定向质疑—修正，仍有分歧才仲裁或转人工。
7. 分歧仲裁和平台规则确定待复核案件；质检操作员查看当前与历史上下文、证据和 Agent 判断，提交决定并留下审计记录。
8. 仪表盘展示任务状态、质检趋势、风险案件和待处理数量；报告由该操作员导出。

## 3. 与现有项目的融合原则

- 保留根目录现有 app/，继续作为 FastAPI 后端；不必把当前项目整体改名为 backend/。
- 新增根目录 frontend/，作为独立的后台单页应用。前端负责展示和操作，不负责评分或身份验证；MVP 只有一个登录账号和一个工作空间。
- 保留现有 app/agents/、app/skills/、app/evaluation/ 和 app/application/orchestration/。这些模块是评价引擎的核心扩展点。
- 在 API、业务用例和领域模型中补入风险案件、人工复核和审计概念；MVP 暂不引入租户、成员、角色和组织管理。
- 比赛版仍采用一个 FastAPI 模块化单体。任务量增长后再考虑外部任务队列、专用数据库或服务拆分。

## 5. 后台优先实现的页面

### 质检总览

展示任务完成情况、各质检维度趋势、待复核数量、处理时长和数据覆盖情况。样本不足时显示样本数和统计时间范围，不生成误导性的排行榜。

### 风险中心

按风险类别、等级、时间和处理状态筛选案件。风险指标需配置来源、触发依据和复核时限；模型发现只生成待确认线索，由唯一操作员处理。

### 复核工作台

展示脱敏后的本次对话时间线、单独标注的复诊历史片段、被引用的消息原文、Hook 候选及规则版本、D6.1/D6.2 各负责 Agent 的结论、单一证据核验 Agent 对原文定位/评分依据/指标定义的核验状态、不同评价 Agent 的意见和历史复核记录。唯一操作员可以确认、驳回、修正或标记无法判断，并填写理由。

### 指标与版本管理

展示当前发布版本、适用范围、评分锚点、示例和审核人。发布新版本时保留旧版本；已有评价报告应记录实际使用的 Skill/规则版本。

## 6. 建议的 API 契约

- GET /api/v1/dashboard/overview：单一工作空间的质检总览。
- POST /api/v1/sessions/import：导入或接收已授权的会话。
- POST /api/v1/evaluations：创建评价任务。
- GET /api/v1/evaluations/{evaluation_id}：查询运行状态和阶段结果。
- GET /api/v1/reports/{report_id}：查看报告与证据。
- GET /api/v1/review-cases：检索待复核案件。
- POST /api/v1/review-cases/{case_id}/decision：提交人工复核决定。
- GET /api/v1/audit-events：按权限查询审计事件。

MVP 不接受客户端提交的 tenant_id 或 workspace_id 来改变数据范围。服务端验证唯一操作员账号，并以当前部署配置确定工作空间；将来支持多平台客户时，再从认证上下文解析租户并在仓储查询处持续施加租户过滤。

## 7. MVP 数据边界与后续多租户扩展

比赛 MVP 使用单一平台工作空间，不建立租户管理和用户成员关系。核心业务记录应有稳定 ID，审计事件记录操作者和时间：

- 会话与消息；
- 评价任务、Agent 运行和报告；
- 风险案件与复核决定；
- 指标配置、发布版本和集成数据源；
- 审计事件。

MVP 仅配置一个平台质检操作员账号，不做角色区分、邀请和案件分派。会话查看、导出和人工修改决定仍应留下审计记录。真实咨询内容应按数据最小化原则处理，演示优先使用合成数据。未来进入多平台商业部署时，再引入服务端租户上下文和角色权限；不得信任客户端提交的 tenant_id。

## 8. 推荐落地顺序

### 第一步：单账号演示闭环

先支持一个演示工作空间和一个操作员账号，完成会话导入、Mock Agent 评价、证据跳转、人工复核和报告页面。不实现成员管理、角色切换、案件分派或租户字段。

### 第二步：运营后台

接入本地持久化、任务状态查询、风险队列、指标版本、审计记录和导出。前端先完成总览、复核工作台、任务详情三个页面。

### 第三步：真实模型接入与产品化权限

替换或并行接入真实 LLM Provider；用专家复核样本检查一致性、证据定位和风险漏报。若进入多平台商业部署，再增加租户管理、成员和角色权限、数据保留策略及平台集成。

## 9. 暂不建议的范围

- 早期拆成多个微服务或上复杂任务编排平台。
- 为了展示而不断增加 Agent 数量；新增指标优先使用 Skill。
- 让模型直接决定最终处罚、医疗风险处置或未经复核的排名。
- 在没有专家基准和足够样本时展示“医生总榜”或宣称准确率。
- 通过文本相似度猜测患者身份，或在没有可信匿名映射、授权、访问审计和删除策略时读取历史咨询。
- 将 Hook 命中直接当作风险定论、评分或自动处罚依据。

## 10. 与当前代码的差距

当前代码已有 FastAPI 入口、领域数据结构、Agent/Skill/Tool 注册接口、简单路由、确定性引用定位基础工具、报告构造和内存仓储接口。统一证据核验 Agent 尚未实现；下列功能仍需实现后，后台页面才有稳定的数据来源：

- 可用的会话导入 API 与脱敏流程；
- 已注册的具体评价 Agent 和端到端评价用例；
- 初诊/复诊识别、历史咨询检索 Tool、带来源标签的历史上下文注入和检索审计；
- 可选风险监测 Hook、按二级指标默认分配 D6 的路由机制及其案件规则；
- 一个涵盖原文定位、评分依据核查、指标定义校对的证据核验子 Agent、一次定向复评和未决转人工流程；
- 持久化的会话、任务、风险案件、报告和复核记录；
- 证据不足/高风险时的复核状态流；
- 单账号登录验证和受保护的 API 查询；
- 为前端提供的列表、筛选、统计和审计 API；
- 登录访问控制和核心业务的自动化测试。
