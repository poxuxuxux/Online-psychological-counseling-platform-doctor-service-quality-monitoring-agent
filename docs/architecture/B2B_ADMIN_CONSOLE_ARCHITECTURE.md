# B2B 风控与服务质检后台：架构融合提案

> 文档状态：面向比赛 MVP 的架构提案，不代表相关功能已经实现。

## 1. 产品定位

产品面向在线心理咨询平台的运营、质检和风控团队。平台方通过后台配置评价规则、查看自动质检结果、处理高风险或低置信案例，并追溯模型结论对应的会话证据。

系统减少人工逐条筛查的工作量，采用“自动初筛和评价 + 人工处理需要复核的案例”的工作方式。评价结果是质检线索；指标和风险规则应由业务及心理咨询专业人员审核，系统不作临床诊断，也不应让未复核的模型评分直接触发处罚。

## 2. 核心业务闭环

1. 平台接入或导入已授权的咨询记录。
2. 后端校验格式、租户归属和数据权限，规范化消息并执行必要的脱敏。
3. 根据平台、业务线和已发布的指标版本创建评价任务。
4. 确定性路由器选择 Skill 和职责明确的 Agent；各 Agent 返回结构化结论及消息证据。
5. 证据核验器验证引用、发言人和必需字段；风险或证据不足的结果进入人工复核队列。
6. 质检人员在后台查看证据、作出复核决定并留下审计记录。
7. 仪表盘展示任务状态、质检趋势、风险案件和复核工作量；报告可按权限导出。

## 3. 与现有项目的融合原则

- 保留根目录现有 app/，继续作为 FastAPI 后端；不必把当前项目整体改名为 backend/。
- 新增根目录 frontend/，作为独立的后台单页应用。前端负责展示和操作，不负责评分、权限裁决或租户隔离。
- 保留现有 app/agents/、app/skills/、app/evaluation/ 和 app/application/orchestration/。这些模块是评价引擎的核心扩展点。
- 在 API、业务用例和领域模型中补入租户、风险案件、人工复核和审计概念。
- 比赛版仍采用一个 FastAPI 模块化单体。任务量增长后再考虑外部任务队列、专用数据库或服务拆分。

## 5. 后台优先实现的页面

### 质检总览

展示任务完成情况、各质检维度趋势、待复核数量、处理时长和数据覆盖情况。样本不足时显示样本数和统计时间范围，不生成误导性的排行榜。

### 风险中心

按风险类别、等级、时间、组织和处理状态筛选案件。风险指标需配置来源、触发依据和复核时限；模型发现只生成待确认线索。

### 复核工作台

展示脱敏后的对话时间线、被引用的消息原文、Agent 结论、证据核验状态、不同 Agent 的意见和历史复核记录。复核人员可以确认、驳回、修正或标记无法判断，并填写理由。

### 指标与版本管理

展示当前发布版本、适用范围、评分锚点、示例和审核人。发布新版本时保留旧版本；已有评价报告应记录实际使用的 Skill/规则版本。

## 6. 建议的 API 契约

- GET /api/v1/dashboard/overview：当前租户的质检总览。
- POST /api/v1/sessions/import：导入或接收已授权的会话。
- POST /api/v1/evaluations：创建评价任务。
- GET /api/v1/evaluations/{evaluation_id}：查询运行状态和阶段结果。
- GET /api/v1/reports/{report_id}：查看报告与证据。
- GET /api/v1/review-cases：检索待复核案件。
- POST /api/v1/review-cases/{case_id}/decision：提交人工复核决定。
- GET /api/v1/audit-events：按权限查询审计事件。

API 不信任请求体中由前端自行填写的 tenant_id。租户身份应从已验证的登录上下文取得，并在仓储查询处持续施加租户过滤。

## 7. B2B 必须提前确定的数据边界

核心记录至少需要带有服务器确认的租户归属，例如 organization_id：

- 会话与消息；
- 评价任务、Agent 运行和报告；
- 风险案件与复核决定；
- 指标配置、发布版本和集成数据源；
- 用户成员关系与审计事件。

角色至少区分平台管理员、质检主管、复核人员和只读审计人员。每个角色对应明确操作权限。查询、导出和人工修改决定均应留下审计记录。真实咨询内容应按数据最小化原则处理，演示优先使用合成数据。

## 8. 推荐落地顺序

### 第一步：单租户演示闭环

先支持一个演示租户，完成会话导入、Mock Agent 评价、证据跳转、人工复核和报告页面。保留租户字段和依赖注入边界，但不急着实现企业级 SSO 或复杂组织层级。

### 第二步：运营后台

接入本地持久化、任务状态查询、风险队列、指标版本、审计记录和导出。前端先完成总览、复核工作台、任务详情三个页面。

### 第三步：真实模型与多租户强化

替换或并行接入真实 LLM Provider；用专家复核样本检查一致性、证据定位和风险漏报。再增加正式租户管理、细粒度角色权限、数据保留策略和平台集成。

## 9. 暂不建议的范围

- 早期拆成多个微服务或上复杂任务编排平台。
- 为了展示而不断增加 Agent 数量；新增指标优先使用 Skill。
- 让模型直接决定最终处罚、医疗风险处置或未经复核的排名。
- 在没有专家基准和足够样本时展示“医生总榜”或宣称准确率。
- 开启跨会话患者记忆，除非可信身份映射、授权、访问审计和删除策略已落实。

## 10. 与当前代码的差距

当前代码已有 FastAPI 入口、领域数据结构、Agent/Skill/Tool 注册接口、简单路由、证据核验、报告构造和内存仓储接口。下列功能仍需实现后，后台页面才有稳定的数据来源：

- 可用的会话导入 API 与脱敏流程；
- 已注册的具体评价 Agent 和端到端评价用例；
- 持久化的租户、会话、任务、风险案件、报告和复核记录；
- 证据不足/高风险时的复核状态流；
- 按租户和角色约束的 API 与查询；
- 为前端提供的列表、筛选、统计和审计 API；
- API、租户隔离和核心业务的自动化测试。
